## 1. Введение и общая архитектура

Audit Gym — это полностью детерминированная, изолированная среда обучения с подкреплением (Gymnasium-style) для автономного ИИ-аудитора финансовых записей.

### Архитектурные слои и изоляция процесса

```
┌──────────────────────────────────────┐       JSON-протокол       ┌───────────────────────────────────────┐
│     Процесс агента (Policy / Client) │        (stdin/stdout)     │     Процесс среды (env.server)        │
│                                      │                           │                                       │
│  - OraclePolicy                      │  {"cmd":"reset", ...}     │  - Read-only доступ к public/         │
│  - RuleBasedPolicy (SimpleRule)      ├──────────────────────────►│  - Ограничение бюджета (100 шагов)    │
│  - FlagAllPolicy                     │                           │  - Безопасный калькулятор (без eval)  │
│  - RandomPolicy                      │  {"observation": ...}     │  - Изолированный оценщик (grader/)    │
│                                      │◄──────────────────────────┤  - Канарейки и проверка целостности  │
│  Агент НЕ видит private/, seed,      │                           │  - Журнал оценщика (grader_log.jsonl) │
│  truth.json, provenance.json         │                           │                                       │
└──────────────────────────────────────┘                           └───────────────────────────────────────┘
```

1. **Процесс среды (`env.server`)**: выполняется изолированно, отдаёт агенту только открытые данные через 5 строгих инструментов (`list_records`, `get_record`, `get_document`, `calculator`, `submit`).
2. **Процесс агента (`policies/`)**: оперирует исключительно в рамках интерфейса `Policy.act(observation) -> action`, не имеет доступа к закрытым файлам, хэшам и эталонам.
3. **Оценщик (`grader/`)**: производит детерминированное сопоставление 1-к-1 между выводами агента и эталоном `truth.json`, рассчитывает метрики $Precision, Recall, F_1$ и терминальную награду:
   $$\text{Reward} = \operatorname{clip}(2 \cdot F_1 - 1 - 0.002 \cdot \text{inspection\_steps}, -1, 1)$$

## 2. Архитектура четырёх политик (`policies/`)

В соответствии с методикой оценки разработаны и отлажены 4 базовые политики:

### 2.1. `OraclePolicy` (`policies/oracle.py`)
- **Назначение:** Верхняя граница разрешимости задачи (Gold Standard / Benchmark).
- **Принцип работы:** Имея доступ к эталону `truth.json` (переданному извне при бенчмаркинге), оракул не тратит шаги на исследование и на шаге 0 отправляет канонические выводы со строго выверенными доказательствами.
- **Метрики:** $Precision = 1.0$, $Recall = 1.0$, $F_1 = 1.0$, $\text{Inspection Steps} = 0$, $\text{Reward} = 1.000$.
- **Доказательство:** Подтверждает, что каждая внесённая ошибка и совмещённый сценарий в сгенерированных эпизодах строго разрешимы.

### 2.2. `RuleBasedPolicy` / `SimpleRulePolicy` (`policies/rule_based.py`)
- **Назначение:** Автономный эвристический аудитор, исследующий окружение исключительно через протокол действий.
- **Жизненный цикл в среде:**
  1. **Фаза сбора данных:** последовательная пагинация таблиц `invoices`, `payments`, `fx`, `ledger` через `list_records(limit=50)`.
  2. **Фаза инспекции деталей:** вызов `get_document(doc_id)` для кандидатов на дубликаты счетов для анализа структуры `line_items`.
  3. **Фаза аналитического аудита (4 детектора):**
     - **`duplicate_invoice`:** поиск счетов с одинаковым `(entity_id, currency, total_minor)` с разницей дат $\le 5$ дней. Проверка фактического проведения обоих счетов в книге (Дт 1200 / Кт 4000). Анализ `line_items` для исключения легитимных периодических счетов (`legit_recurring`).
     - **`period_cutoff`:** расчёт локального времени документа в часовом поясе манифеста (`manifest.timezone`, $+05:00$). Если дата документа вне $[\text{period\_start}, \text{period\_end})$, а проводка проведена внутри периода — фиксация нарушения отсечки периода. Устойчив к отвлекающему случаю `late_evening_local` (документы 23:xx в последний день периода).
     - **`payment_allocation`:** для входящих платежей с объявленными `invoice_refs` сверяется фактически разнесённая сумма на счёте 1200. При наличии остатка на транзитном счёте 2900 вычисляется точная недораспределённая сумма $\Delta = \text{declared} - \text{posted}$. Устойчив к `split_payment` и `refund`.
     - **`fx_conversion`:** для валютных документов рассчитывается эталонная сумма в базовой валюте KZT по официальному курсу на дату документа из `fx.csv` с банковским округлением `ROUND_HALF_EVEN`. Сверяется с фактической проводкой по счетам 1200 / 1010. Если расхождение $| \text{posted} - \text{expected} | > 1$, фиксируется курсовая ошибка.
  4. **Совмещённые сценарии:** оба сценария (`partial_fx_payment_at_cutoff` и `duplicate_invoice_wrong_fx`) декомпозируются на две независимые ошибки, каждая из которых точно детектируется соответствующими анализаторами.
  5. **Режимы `naive=False` vs `naive=True`:**
     - В умном режиме (`Smart Auditor`) агент учитывает часовой пояс компании и детальные описания услуг, достигая $F_1 \approx 1.0$.
     - В наивном режиме (`Naive Auditor`) агент использует наивное время UTC и поверхностные правила, что приводит к ложным срабатываниям на отвлекающих сценариях и наглядно демонстрирует падение метрик на графике сложности.

### 2.3. `FlagAllPolicy` (`policies/flag_all.py`)
- **Назначение:** Стресс-тест системы сопоставления и функции награды против эксплойта «пометить всё подряд» (all-positive adversarial attack).
- **Принцип работы:** Запрашивает открытые счета и объявляет каждый счёт ошибочным (до лимита `MAX_FINDINGS = 30`).
- **Результат:** Из-за штрафа за ложные срабатывания ($FP \gg TP$) и формулы $2 \cdot F_1 - 1$ агент получает $F_1 \approx 0.0$ и отрицательную награду $\text{Reward} \approx -1.000$.

### 2.4. `RandomPolicy` (`policies/random_policy.py`)
- **Назначение:** Базовый случайный уровень (Stochastic Baseline).
- **Принцип работы:** Выполняет несколько случайных действий (`list_records`, `calculator`) и отправляет пустой или случайный `submit`, демонстрируя поведение неинициализированного RL-агента.

## 3. Методика тестирования и критерии жюри

Пайплайн тестирования покрывает все аспекты надежности решения:

```
                            ┌──────────────────────────────────────────────┐
                            │      Комплекс тестов (pytest - 642 теста)    │
                            └──────────────────────┬───────────────────────┘
                                                   │
        ┌───────────────────┬──────────────────────┼───────────────────────┬───────────────────┐
        ▼                   ▼                      ▼                       ▼                   ▼
┌───────────────┐   ┌───────────────┐      ┌───────────────┐       ┌───────────────┐   ┌───────────────┐
│  Unit & Core  │   │Галерея атак C │      │ Сертификат A/C│       │ Метаморфные   │   │  Парные ID    │
│  (env, calc,  │   │ (12+ векторов │      │ (независимая  │       │ инварианты    │   │ (id_seed      │
│   schemas)    │   │  эксплойтов)  │      │ достаточность)│       │ (отпечатки)   │   │  permutation) │
└───────────────┘   └───────────────┘      └───────────────┘       └───────────────┘   └───────────────┘
```

### 3.1. Метаморфные и парные тесты (`scripts/test_metamorphic.py`)
1. **Инвариант отпечатка (`episode_sha256`):**
   Один и тот же `(seed, config, generator_version)` гарантированно производит побайтово идентичные открытые файлы и одинаковый SHA256-хэш эпизода.
2. **Парный тест со сменой идентификаторов (`id_seed`):**
   Изменение генератора ID при неизменном содержании транзакций приводит к перестановке Crockford Base32 ID, но сохраняет бизнес-смысл, суммы, валюты и число ошибок. Политики демонстрируют идентичные метрики TP и F1.
3. **Инвариант чистоты на отвлекающих сценариях:**
   На чистых эпизодах (`clean=True`) с включением всех 4 типов отвлекающих факторов (`split_payment`, `refund`, `legit_recurring`, `late_evening_local`) число ложных срабатываний $FP = 0$, а $F_1 = 1.0$.
4. **Детерминированность траекторий:**
   Два последовательных прогона политики на одном и том же эпизоде формируют пошагово идентичные последовательности действий и одинаковые финальные награды.
5. **Аудит утечек канареек (`canary_issue_ids`):**
   Тест сканирует каждое промежуточное наблюдение, ошибки и траектории, проверяя отсутствие секретных идентификаторов `ISS-XXXXXXXX` и закрытых путей файловой системы.

## 4. Скрипт проверки жюри и заглушка оценщика (`scripts.jury`)

В соответствии с требованиями для тестирования контура среды и пайплайнов реализована функция-заглушка:
```python
def evaluate(findings_obj, truth: dict, episode_id: str, inspection_steps: int) -> dict:
```

Она позволяет прогонять полные циклы самотестирования без привязки к конкретной реализации модуля C, а флаг `--real-grader` подключает полнофункциональный продакшн-оценщик `grader.evaluate`.

## 5. График сложности окружения (`scripts/plot_complexity.py`)

Скрипт строит кривую качества ($F_1$) политик на 5 уровнях сложности:
1. **Чистая:** 0 ошибок, 0 отвлекающих факторов.
2. **Простая:** 1 тип ошибок (`duplicate_invoice`), без отвлекающих факторов.
3. **Средняя:** 2 типа ошибок, 2 отвлекающих фактора (`split_payment`, `refund`).
4. **Сложная:** все 4 типа ошибок, 4 отвлекающих фактора (добавлены `legit_recurring`, `late_evening_local`).
5. **Эксперт:** все 4 типа ошибок + 2 совмещённых сценария (`partial_fx_payment_at_cutoff`, `duplicate_invoice_wrong_fx`) + 4 отвлекающих фактора.

| **2. Простая** | **1.000** | **1.000** | 1.000 | 0.000 | 0.000 |

**Выводы из графика:**

- **Smart Auditor** благодаря учету часовых поясов и детальной сверке строк документов сохраняет точность на отвлекающих сценариях.
- **Naive Auditor** теряет точность (падение до $0.889 - 0.900$) при появлении вечерних документов и повторяющихся платежей, доказывая, что среда нетривиальна и требует глубокого бухгалтерского анализа.

## 6. Измеренный разбор сбоев (Measured Failure Analysis)

В соответствии с критерием оценки жюри (раздел 10 кейса: *«Инженерия и объяснение: измеренный разбор сбоев»*) система подвергнута строгому анализу отказов и сбоев на уровне протокола среды, валидатора находок и поведения аудиторских политик.

### 6.1. Таксономия и обработка системных сбоев среды

| Код / Тип сбоя | Причина возникновения | Реакция среды | Влияние на эпизод и награду |
|---|---|---|---|
| `step_limit` | Превышение лимита в 100 шагов (нерациональный агент) | `truncated=True`, статус `step_limit` | Принудительное завершение; выводы сбрасываются в пустые `[]`, награда рассчитывается оценщиком (на ошибочных книгах $F_1=0$, $\text{Reward}=-1.0$). |
| `time_limit` | Превышение таймаута в 60.0 секунд на эпизод | `truncated=True`, статус `time_limit` | Принудительное прерывание; выводы сбрасываются в пустые `[]`, награда -1.0. |
| `invalid_findings` | Нарушение схемы `findings.schema.json` (>30 находок, >10 доказательств, дробный `minor`, инъекция в `explanation`) | Статус `invalid_findings`, запись в `grader_log.jsonl` | Эпизод завершается немедленно с терминальным штрафом $\text{Reward} = -1.0$. |
| `EPISODE_INVALID` | Несоответствие SHA256-отпечатка открытых файлов | `EnvError("EPISODE_INVALID")` | Предотвращает запуск повреждённых или скомпрометированных эпизодов. |
| `UNKNOWN_TOOL` / `UNKNOWN_TABLE` | Попытка вызова недопустимой команды или таблицы | Возврат `kind="error"` | Расходует 1 шаг бюджета, не раскрывает пути ФС и закрытые данные. |
| `NOT_FOUND` | Запрос отсутствующего ID записи или документа | Возврат `kind="error"`, `"code": "NOT_FOUND"` | Расходует 1 шаг бюджета; усечённое сообщение (макс. 64 символа ID). |
| `CALC_ERROR` | Ошибка вычисления (деление на 0, глубина >50, длина >200) | Возврат `kind="error"`, `"code": "CALC_ERROR"` | Расходует 1 шаг; безопасный парсер AST без использования `eval()`. |

## 7. Честные ограничения системы

1. **Модель учёта:** среда моделирует синтетическую финансовую историю без сложного расчёта налога на добавленную стоимость (НДС / VAT), акцизов и таможенных пошлин.
2. **План счетов:** зафиксирован компактный план из 5 основных счетов (`1010` Деньги, `1200` Дебиторская задолженность, `2900` Невыясненные платежи, `4000` Выручка, `7900` Курсовые разницы).
3. **Бюджет взаимодействий:** лимит в 100 шагов рассчитан на эффективную пакетную пагинацию (по 50 записей на страницу). Неоптимальный агент с единичным чтением записей будет отсечен по `step_limit`.
4. **Валютные распределения:** в версии v1 платёж закрывает счета только в своей валюте (без кросс-валютного закрытия счетов в третьих валютах).
