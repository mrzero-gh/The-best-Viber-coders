## 1. Введение и общая архитектура

Audit Gym — это полностью детерминированная, изолированная среда обучения с подкреплением (Gymnasium-style) для автономного ИИ-аудитора финансовых записей.

### Архитектурные слои и изоляция процесса

```
┌──────────────────────────────────────┐       JSON-протокол       ┌───────────────────────────────────────┐
│     Процесс агента (Policy / Client) │        (stdin/stdout)     │     Процесс среды (env.server)        │
│                                      │                           │                                       │
│  - OraclePolicy                      │  {"cmd":"reset", ...}     │  - Read-only доступ к public/         │
│  - RuleBasedPolicy (SimpleRule)      ├──────────────────────────►│  - Ограничение бюджета (100 шагов)    │
│  - FlagAllPolicy                     │                           │  - Безопасный калькулятор (без eval)  │
│  - RandomPolicy                      │  {"observation": ...}     │  - Изолированный оценщик (grader/)    │
│                                      │◄──────────────────────────┤  - Канарейки и проверка целостности  │
│  Агент НЕ видит private/, seed,      │                           │  - Журнал оценщика (grader_log.jsonl) │
│  truth.json, provenance.json         │                           │                                       │
└──────────────────────────────────────┘                           └───────────────────────────────────────┘
```

1. **Процесс среды (`env.server`)**: выполняется изолированно, отдаёт агенту только открытые данные через 5 строгих инструментов (`list_records`, `get_record`, `get_document`, `calculator`, `submit`).
2. **Процесс агента (`policies/`)**: оперирует исключительно в рамках интерфейса `Policy.act(observation) -> action`, не имеет доступа к закрытым файлам, хэшам и эталонам.
3. **Оценщик (`grader/`)**: производит детерминированное сопоставление 1-к-1 между выводами агента и эталоном `truth.json`, рассчитывает метрики $Precision, Recall, F_1$ и терминальную награду:
   $$\text{Reward} = \operatorname{clip}(2 \cdot F_1 - 1 - 0.002 \cdot \text{inspection\_steps}, -1, 1)$$

## 2. Модель данных, генератор и эталон (Критерий «Данные и эталон» — 25 баллов)

### 2.1. Что моделирует генератор

Каждый эпизод — один отчётный месяц вымышленной компании. Тип компании задаётся конфигурацией: импортёр электроники, SaaS с подписками или оптовый дистрибьютор.
* **Базовая валюта:** KZT (Казахстанский тенге).
* **Часовой пояс:** `+05:00` (Астана / Алматы).
* **Иностранные валюты контрагентов:** USD, CNY, EUR, RUB и JPY.
* **Показатель разрядности валюты:** у иены (JPY) 0 знаков после запятой, у остальных — 2 знака (`exponents`).
* **Форматы значений:**
  - Деньги — целые числа в минимальных неделимых единицах (тиыны, центы, иены);
  - Курсы валют — точные десятичные строки;
  - Метки времени — ISO-8601 с явным смещением часового пояса;
  - Отсутствующие ссылки — явный `null`.
  - Тип `float` нигде в финансовых вычислениях не используется (исключение ошибок округления IEEE 754).

Агенту доступны только 6 открытых файлов в каталоге `public/`: `manifest.json`, `ledger.csv`, `invoices.jsonl`, `payments.jsonl`, `fx.csv`, `policy.json`. Файлы эталона (`truth.json`), причинной истории изменений (`provenance.json`) и параметры генерации изолированы в `private/` и агенту недоступны.

### 2.2. Бухгалтерская модель учёта и инвариант баланса (Дт = Кт)

Главная книга ведётся в базовой валюте KZT. В каждой строке строго одна сторона проводки больше нуля.

| Документ | Формируемые проводки |
|---|---|
| **Счёт (Invoice)** | Дт 1200 (Дебиторская задолженность) на сумму `total × курс(дата счёта)`; Кт 4000 (Выручка) по позициям спецификации, последняя строка закрывает копейки округления. |
| **Платёж (Payment)** | Дт 1010 (Банковский счёт) на сумму `amount × курс(дата платежа)`; Кт 1200 по каждому счёту из выписки по курсу даты счёта; нераспределённый остаток уходит на Кт 2900 (Невыясненные поступления); курсовая разница относится на 7900. |
| **Возврат (Refund)** | Сторнирующие проводки: Кт 1010, Дт 1200. |

**Фундаментальный инвариант среды:**
Дебет строго равен кредиту по каждому первичному документу и суммарно по всей книге ($Дт = Кт$). Баланс проверяется на каждом сгенерированном эпизоде до и **после внесения искажений**: внесённые ошибки изменяют структуру и адресацию проводок, но сохраняют равенство баланса. Поэтому выявить ошибки простой проверкой сходимости книги невозможно — требуется полноценный аудит первичных документов.

### 2.3. Четыре типа ошибок учёта

| Тип ошибки | Механизм внесения | Проявление в открытых данных | Допустимые доказательства |
|---|---|---|---|
| `duplicate_invoice` | Создаётся полная копия счёта: новый ID, тот же контрагент и спецификация, дата сдвинута на 0–5 дней; проведена повторно. | Два одинаковых счёта близко по дате, оба отражены в проводках книги. | ID обоих документов счетов (`DOC-XXXXXXXX`). |
| `payment_allocation` | По выписке платёж закрывает счёт целиком, а в книге на счёт 1200 разнесена лишь часть (20–80 %), остаток ушёл на 2900. | Выписка и книга расходятся, счёт 1200 остался незакрытым, остаток висит на 2900. | Документ платежа и все связанные строки книги (`PAY-...`, `L-...`). |
| `fx_conversion` | Применён курс другой даты (±1–5 дней) либо искажённый на 1–5 % (расхождение $\ge 100$ минорных единиц). | Проводка в книге не равна `сумма × курс(дата документа)`. | Документ, строка проводки книги, котировка `FX:YYYY-MM-DD:...`. |
| `period_cutoff` | Документ датирован за пределами отчётного периода (до 7 дней), а проведён внутри периода. | Дата документа вне периода, а дата проводки книги — внутри. | Документ и соответствующая строка книги. |

Каждый тип настраивается в конфиге отдельно (`enabled`, `count: [min, max]`). Общий лимит ошибок в эпизоде $\le 12$. Ошибки не делят первичные документы: пара `(type, affected_ids)` строго уникальна, исключая неоднозначность при оценке.

### 2.4. Взаимодействующие совмещённые сценарии

Совмещённый сценарий представляет собой две взаимосвязанные ошибки на одних и тех же записях, каждая из которых оценивается в $F_1$ независимо:
1. `partial_fx_payment_at_cutoff`: валютный платёж датирован после окончания отчётного периода, проведён в периоде и распределён с остатком на 2900. Декомпозируется на `period_cutoff` (по платежу) и `payment_allocation` (по паре счёт-платёж).
2. `duplicate_invoice_wrong_fx`: дубликат валютного счёта проведён с искажением валютного курса. Декомпозируется на `duplicate_invoice` (оригинал и копия) и `fx_conversion` (по дубликату).

### 2.5. Отвлекающие сценарии (Distractors)

Для проверки устойчивости функции награды и защиты от ложных обвинений добросовестных контрагентов генератор моделирует 4 легитимных отвлекающих фактора:

| Отвлекающий фактор | Внешнее сходство с ошибкой | Почему операция законна |
|---|---|---|
| `split_payment` | Счёт закрывается несколькими частичными платежами. | Сумма платежей точно равна счёту, каждый распределён без остатка на 2900, задолженность закрыта до тиына. |
| `refund` | Отрицательный платёж и сторнирующие проводки. | Привязан к исходному платежу, не превышает его сумму, курсовые разницы рассчитаны верно. |
| `legit_recurring` | Тот же контрагент, одинаковая сумма в пределах месяца. | Разные месяцы и разные периоды оказания услуг в спецификации (`line_items`); прошлый счёт закрыт в своём периоде. |
| `late_evening_local` | Документ датирован 23:xx последнего дня месяца. | По местному времени компании (`+05:00`) он строго внутри отчётного периода, хотя в UTC уже наступил следующий день. |

Отвлекающие факторы присутствуют даже в абсолютно чистых компаниях (`clean: true`), поэтому политика «пометить всё подозрительное» получает отрицательную награду (до $-1.000$).

### 2.6. Математическая разрешимость и независимый сертификат

* **Полная котировочная сетка:** файл `fx.csv` содержит курсы на каждый календарный день от `period_start - 10` до `period_end + 10` дней.
* **Независимая верификация (`grader.certificate`):** отдельный модуль, написанный независимо, проверяет каждый эпизод: пересчитывает расхождения только по открытым данным, подтверждает достаточность доказательств и легитимность отвлекающих факторов. 100% сгенерированных эпизодов успешно получают сертификат разрешимости.
* **Причинная цепочка (`generator.explain`):** команда `python -m generator.explain <эпизод>` восстанавливает полную детективную историю искажений из `provenance.json` для проверяющего.

### 2.7. Детерминизм и псевдослучайные потоки

Все случайные величины генерируются изолированными экземплярами `random.Random`, засеянными от `sha256(f"{seed}:{поток}")`. Используются 4 независимых потока: `content`, `ids`, `errors`, `distractors`. Смена `id_seed` меняет строковые идентификаторы без изменения финансовой сущности операций, что обеспечивает надёжность парных тестов.

## 3. Архитектура базовых политик (`policies/`)

В соответствии с методикой оценки организаторов (раздел 06 регламента) разработаны 4 базовые политики:

### 3.1. `OraclePolicy` (`policies/oracle.py`)
* **Назначение:** Верхняя теоретическая граница качества ($F_1 = 1.000, \text{Reward} = +1.000$).
* **Принцип:** Имея эталон `truth.json`, на шаге 0 отправляет канонические выводы с доказательствами, подтверждая разрешимость эпизода.

### 3.2. `SmartAuditor` / `RuleBasedPolicy(naive=False)` (`policies/rule_based.py`)
* **Назначение:** Автономный эвристический аудитор, исследующий среду через инструменты:
  1. Пагинирует таблицы через `list_records(limit=50)`;
  2. Запрашивает через `get_document(doc_id)` спецификации подозрительных счетов;
  3. Построчно сопоставляет `line_items` для исключения `legit_recurring`;
  4. Переводит время в часовой пояс компании (`+05:00`), нейтрализуя ловушку `late_evening_local`;
  5. Сверяет счёт 2900, исключая ложные срабатывания на `split_payment` и `refund`.
* **Результат:** $F_1 \approx 1.000$, $\text{Reward} \ge +0.950$.

### 3.3. `SimpleRulePolicy` (`policies/rule_based.py`)
* **Назначение:** Простая поверхностная сверка (Naive Baseline).
* **Принцип:** Не запрашивает спецификации первичных документов, использует наивное время UTC и игнорирует счёт 2900.
* **Результат:** Падает по $F_1$ до $0.88 - 0.90$ на отвлекающих сценариях, наглядно доказывая нетривиальность задачи на графике сложности.

### 3.4. `FlagAllPolicy` (`policies/flag_all.py`)
* **Назначение:** Стресс-тест функции награды (Adversarial Baseline). Маркирует все найденные документы как ошибочные. Оценщик детерминированно начисляет штраф за ложные срабатывания ($F_1 = 0.000, \text{Reward} = -1.000$).

## 4. Скрипт проверки методикой жюри (`scripts.jury`)

Модуль `scripts/jury.py` запускает воспроизведение закрытой проверки жюри:
1. По умолчанию подключает боевой оценщик `grader.evaluate:evaluate`;
2. Прогоняет базовые политики на 4 репрезентативных сценариях (чистые компании с отвлекающими случаями, одиночные ошибки, совмещённые сценарии, полный комплекс);
3. **Динамически рассчитывает баллы** по фактическим результатам:
   - *Данные и эталон (25):* $\text{round}(25 \times F_{1,\text{oracle}})$;
   - *Контракт и изоляция (25):* валидность шагов $\le 100$, завершение по submit;
   - *Надёжность награды (25):* отражение атаки FlagAll ($\text{Reward} \le -1.0$);
   - *Воспроизводимость (15):* детерминизм прогона;
   - *Инженерия (10):* среднее время на эпизод $< 60$ сек.

Запуск проверки:
```powershell
python -m scripts.jury
```

## 7. Честные ограничения системы

1. **Модель учёта:** среда моделирует синтетическую финансовую историю без расчёта налога на добавленную стоимость (НДС / VAT), акцизов и таможенных пошлин.
2. **План счетов:** компактный рабочий план из 5 основных счетов (`1010` Деньги, `1200` Дебиторская задолженность, `2900` Невыясненные платежи, `4000` Выручка, `7900` Курсовые разницы).
3. **Бюджет взаимодействий:** лимит в 100 шагов ориентирован на пакетную пагинацию (по 50 записей на страницу).
4. **Валютные распределения:** в версии v1 платёж закрывает счета только в своей валюте (без кросс-валютного закрытия счетов в третьих валютах).
5. **Высокая награда:** высокая награда в симуляторе подтверждает математическую корректность расследования, но не доказывает пригодность модели для реального аудита без дообучения на реальной первичной документации.
