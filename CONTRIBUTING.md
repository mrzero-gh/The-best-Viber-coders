# Как работать с репозиторием (GitHub Desktop)

Коротко: **в `main` напрямую не коммитим. Каждый работает в своей ветке и в своих папках, в `main` попадаем только через Pull Request, сливает капитан.**

---

## 0. Один раз: подготовка

1. Установите [GitHub Desktop](https://desktop.github.com/) и войдите: **File → Options → Accounts → Sign in**.
2. Владелец репозитория (`mrzero-gh`) добавляет всех в **Settings → Collaborators → Add people**. Примите приглашение из почты или на github.com.
3. Склонируйте репозиторий: **File → Clone repository → URL** → `https://github.com/mrzero-gh/The-best-Viber-coders` → выберите папку → **Clone**.
   - Лучше клонировать **не в OneDrive** и не в папку с кириллицей или пробелами в пути, например `C:\dev\The-best-Viber-coders`. OneDrive синхронизирует папку `.git` и иногда ломает её, а Docker и часть инструментов плохо работают с кириллицей в пути.
4. Проверьте имя и почту для коммитов: **File → Options → Git**. Почта должна совпадать с почтой аккаунта GitHub, иначе коммиты не привяжутся к вашему профилю.
5. Python 3.11. Создайте окружение внутри папки проекта:
   ```bash
   python -m venv .venv
   ```
   Папка `.venv` уже в `.gitignore`, в репозиторий она не попадёт.

## 1. Каждый раз перед началом работы

1. Вверху **Current branch → main**.
2. **Fetch origin**, затем **Pull origin**: подтянули свежий `main`.
3. **Current branch → New branch** → имя `имя/задача`, например `aidar/fx-error`, `erasyl/matcher`. Основа — **main**.
4. Работаете в этой ветке.

## 2. Коммиты

- Коммитьте **часто и маленькими порциями**: одна логическая правка = один коммит (раз в 30–60 минут).
- Внизу слева: **Summary** — коротко и по делу, глаголом:
  - `Добавил ошибку дубля счёта в генератор`
  - `Matcher: допуск по сумме и выбор при неоднозначности`
  - `Тесты атак на награду`
- Перед коммитом посмотрите список изменённых файлов. Снимите галочки с лишнего (`.venv`, логи, временные файлы).
- **Push origin** — отправить ветку на GitHub (можно после каждого коммита, это безопасно).

## 3. Как попасть в `main`

1. Перед PR подтяните свежий `main` в свою ветку: **Branch → Update from main**. Если есть конфликты, смотрите раздел 5.
2. Запустите тесты локально: `pytest`.
3. **Push origin**, затем **Create Pull Request** (откроется GitHub в браузере).
4. Заполните шаблон PR и нажмите **Create pull request**. Напишите в чат команды.
5. Капитан смотрит и нажимает **Merge**. Сами свои PR не сливаем.
6. После слияния: в Desktop **Current branch → main → Pull origin**. Старую ветку можно удалить (**Branch → Delete**). Следующая задача — новая ветка.

## 4. Кто где работает (чтобы не было конфликтов)

Каждая роль владеет своими папками. Чужие папки правим только по договорённости в чате.

| Роль | Папки |
|---|---|
| A — генератор данных | `generator/`, `tests/test_generator*` |
| B — среда, изоляция, Docker (капитан) | `env/`, `Dockerfile`, `scripts/check.py`, `docs/contract.md`, `schemas/` |
| C — оценщик и награда | `grader/`, `tests/test_grader*`, `tests/test_attacks*` |
| D — политики, эпизоды, документы | `policies/`, `episodes/`, `scripts/` (кроме `check.py`), `README.md`, `docs/design.md` |

Все команды запускаются через Python (`python -m scripts.check`, `python -m scripts.jury`), а не через `make`: у многих на Windows `make` не установлен.

**Общие файлы** (`docs/contract.md`, `schemas/`, `requirements.txt`) меняет только капитан, или через PR с предупреждением в чате: от них зависят все.

## 5. Если конфликт

GitHub Desktop покажет файлы с конфликтом после **Update from main** или **Pull**.

1. Нажмите **Open in Visual Studio Code** (или в своём редакторе).
2. В файле будут блоки:
   ```
   <<<<<<< HEAD
   ваш вариант
   =======
   вариант из main
   >>>>>>> main
   ```
   Оставьте правильный код (иногда нужны обе части), удалите маркеры `<<<<<<<`, `=======`, `>>>>>>>`.
3. Сохраните файл. В Desktop он отметится как решённый. Нажмите **Continue merge** / **Commit merge**.
4. Запустите `pytest`. Не уверены, чей код верный — **спросите автора, не угадывайте**.

## 6. Чего не делать

- Не коммитить в `main` напрямую.
- Не делать **Force push** (в Desktop: «Force push origin»). Это стирает чужую работу.
- Не коммитить `.venv`, `__pycache__`, файлы больше 50 МБ, пароли и токены.
- Не переименовывать и не переносить чужие файлы без предупреждения.
- Не держать ветку днями: чем дольше ветка живёт отдельно от `main`, тем больше конфликтов. Цель — PR каждые 2–4 часа.

## 7. Если что-то пошло не так

| Ситуация | Что делать |
|---|---|
| Закоммитил не то, ещё не запушил | **History** → правый клик по коммиту → **Undo commit** |
| Начал работать в `main` вместо ветки | Ничего не коммитьте. **New branch**, Desktop предложит перенести изменения в новую ветку — выберите **Bring my changes** |
| Нужно переключиться на другую ветку, а изменения не готовы | **Stash all changes** (Desktop предложит сам), потом вернуть: **Stashed changes → Restore** |
| Push отклонён (`rejected`) | Сначала **Pull origin**, потом снова **Push** |
| Сломал что-то и непонятно что | Не делайте ничего с `--force`. Напишите капитану |

## 8. Окончания строк и кодировка

В репозитории есть `.gitattributes` и `.editorconfig`: все файлы хранятся в UTF-8 с окончаниями строк LF. Это нужно, чтобы эпизоды и их хэши были побайтно одинаковыми на Windows и у жюри. Ничего настраивать не нужно. Если редактор спрашивает про CRLF/LF — выбирайте **LF**.
