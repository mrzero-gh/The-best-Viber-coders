## 2. Процессы и изоляция

```
 процесс агента                       процесс среды (env.server)
┌──────────────────────┐   JSON по    ┌───────────────────────────────┐
│ Policy               │   stdin /    │ записи эпизода (public)       │
│   ↕                  │   stdout     │ инструменты (только чтение)   │
│ env.client.AuditEnv ─┼─────────────►│ оценщик: truth, matcher,      │
│  reset / step        │◄─────────────┼─ награда, журнал оценщика     │
└──────────────────────┘              └───────────────────────────────┘
```

- Агент работает только через `AuditEnv.reset/step`. Он **не получает** путей к файлам, seed, `truth`, `provenance`.
- `env.server` — отдельный процесс. Он генерирует или загружает эпизод, держит записи только для чтения и считает награду. Агент не может изменить записи или состояние оценщика: у протокола нет таких команд.
- Протокол: одна JSON-строка на команду, одна на ответ (UTF-8, `\n`).

| Команда клиента | Ответ сервера |
|---|---|
| `{"cmd": "reset", "seed": 42, "config": {...}}` | `{"observation": {...}, "info": {...}}` |
| `{"cmd": "step", "action": {...}}` | `{"observation": {...}, "reward": 0.0, "terminated": false, "truncated": false, "info": {...}}` |
| `{"cmd": "close"}` | `{"ok": true}`, процесс завершается |

### Ошибки протокола
Формат: `{"error": {"code": ..., "message": ...}}`, сообщения фиксированные, без путей и деталей. После ошибки сервер продолжает работать.
- `BAD_REQUEST` — не JSON, не объект, неизвестный `cmd`, лишние/недостающие поля, `seed` не int (в т.ч. bool), строка длиннее 1 МиБ.
- `BAD_CONFIG` — `config` не объект или `mode` не `train`/`eval`.
- `NO_EPISODE` — `step` до `reset`.
- `GENERATION_FAILED` — генератор не создал эпизод.
- `EPISODE_INVALID` — эпизод повреждён: отпечаток не сошёлся с `generation.json` (раздел 15), файл отсутствует или не разбирается, либо оценщик отклонил эталон при `submit` (тогда эпизод закрыт).
- `INTERNAL` — любое неожиданное исключение (трейсбек в stderr только в `train`).

`step` после завершения эпизода — не ошибка протокола, а наблюдение `EPISODE_FINISHED` (раздел 7). EOF на stdin — тихий выход с кодом 0.

### Запуск сервера
`python -m env.server [--run-id ID] [--runs-dir DIR] [--episode PATH [--trust-episode]] [--grader module:func] [--time-limit-s N]`
- `--run-id` — по умолчанию `run-<YYYYmmdd-HHMMSS>-<pid>`; `--runs-dir` — по умолчанию переменная окружения `AUDIT_GYM_RUNS_DIR`, иначе `runs` (в Docker-образе `AUDIT_GYM_RUNS_DIR=/tmp/runs`, потому что код смонтирован только для чтения).
- Контейнер: `python -m scripts.check --docker` собирает образ и запускает проверку с `--network none --read-only --tmpfs /tmp --cpus 2 --memory 4g`, не от root; `tests/test_container.py` внутри подтверждает отсутствие сети и запись только в `/tmp`.
- `--episode PATH` — готовый эпизод с диска (seed игнорируется, из `config` берётся только `mode`); для тестов и dev-эпизодов.
- `--trust-episode` — только с `--episode`: эпизод подал доверенный вызывающий (адаптер жюри, [judge_adapter.md](judge_adapter.md)). Отпечаток (раздел 15) не сверяется с `generation.json`, а пересчитывается по фактическим `public`-файлам и пишется в журнал: жюри в парных проверках само переставляет записи и меняет ID в копии эпизода.
- `--grader`, `--time-limit-s` — **только для тестов** (подмена оценщика и лимита времени).
- Без `--episode` эпизод генерируется во временную папку; после загрузки `public` и `truth` в память папка удаляется целиком.
- Журнал оценщика `<runs-dir>/<run-id>/grader_log.jsonl` (в обоих режимах): строка на завершённый эпизод (любой `status`), поля `run_id`, `episode_id`, `mode`, `seed` (`null` при `--episode`), `config_version` (из `config` или `null`), `status`, `steps_used`, `inspection_steps`, `reward`, `valid`, `error`, `metrics`, `episode_sha256` (отпечаток эпизода, раздел 15; агенту не передаётся). Схема строки — `grader_log.schema.json`.

- `reset` полностью пересоздаёт состояние эпизода: два `reset` подряд ничего не делят.
- Сервер никогда не пишет в stdout ничего, кроме ответов протокола. Отладочный вывод — только в stderr и только в режиме `train`.

### Режимы
`config.mode`:
- `train` — терминальная награда возвращается политике в ответе на завершающий шаг, в `info.metrics` приходят TP/FP/FN/P/R/F1 (только числа, без указания, какие выводы неверны).
- `eval` — `reward` всегда `0.0`, `info` содержит только `episode_id` и `mode`. Награда и диагностика пишутся в журнал оценщика `runs/<run_id>/grader_log.jsonl`, путь к которому агенту не передаётся.

### Аудит утечек
Критерий: ни одной метки эталона и ни одного пути к файлам в наблюдениях, сообщениях `EnvError`, `info` и траекториях. Проверяет `env/leak_audit.py`, тесты - `tests/test_leaks.py`.
- Метки эталона: все `issue_id` и `distractor_id`, названия сценариев и `kind` отвлекающих случаев, ключи `truth` (`issue_id`, `evidence_sets`, ...), `episode_sha256`, `generator_version`, строки `mutations` из `provenance.json` (публичные ID и значения исключаются: агент видит их законно).
- Пути: пути запуска и временных папок, `auditgym-`, `Traceback`, `File "`, `.py"`, `\Users\`, `/home/`, `/tmp/`.
- Сценарии: честный проход по таблицам, oracle, неверный ввод, лимит шагов, протокольный мусор; режимы `train` и `eval`.
- eval-инварианты: `info` ровно `{episode_id, mode}`, `reward` всегда `0.0`, нигде нет `metrics`.
- Канарейки: копия эпизода с метками `ISS-CANARY01`, `DST-CANARY01`, `CANARY-GENERATION-7Q4Z`, `CANARY-PROVENANCE-7Q4Z` в `private/` (`public/` не меняется); строка `CANARY` не должна появиться ни в одном ответе.
- Побочные проверки: после `reset` и `close` не остаётся папок `auditgym-*`; stderr сервера в `eval` пуст; в `public/` нет ID эталона, названий сценариев и слов-подсказок.

Запуск: `python -m env.leak_audit [--seeds 1,2,3] [--out FILE]` - краткий отчёт, код возврата 0 (чисто) или 1 (есть находки), `--out` пишет JSON-отчёт.

## 3. Эпизод на диске

```
episodes/<split>/<episode_id>/
├── public/                 ← то, что среда отдаёт через инструменты
│   ├── manifest.json
│   ├── ledger.csv
│   ├── invoices.jsonl
│   ├── payments.jsonl
│   ├── fx.csv
│   └── policy.json
└── private/                ← только оценщик
    ├── truth.json
    ├── provenance.json
    └── generation.json     ← seed, config, generator_version, sha256 public-файлов
```

`<split>` — `train` или `dev`. Эпизод однозначно воспроизводится из `(seed, config, generator_version)`.

### Форматы значений
- **Время:** ISO-8601 со смещением, точность до секунд: `2026-09-30T23:40:00+05:00`. Без `Z` и без наивного времени.
- **Даты** (в `fx.csv`): `YYYY-MM-DD`, это дата в часовом поясе из `manifest.timezone`.
- **Деньги:** целые числа в минимальных единицах валюты (`*_minor`). Разрядность валюты — в `manifest.currency_exponents` (KZT 2, USD 2, EUR 2, CNY 2, RUB 2, JPY 0).
- **Курсы FX:** десятичные строки, `"470.1500"`. Никаких float.
- **Отсутствующие ссылки:** в JSON/JSONL — `null`. В CSV — пустое поле (объявлено в `manifest.csv_null = ""`). Инструменты отдают их как JSON `null`.
- **ID:** непрозрачные строки `ПРЕФИКС-XXXXXXXX` (8 символов base32 Крокфорда из отдельного RNG-потока `ids`). По ID нельзя угадать порядок или тип ошибки.

| Префикс | Что |
|---|---|
| `EP-` | `episode_id` |
| `L-` | `row_id` проводки |
| `INV-` | `invoice_id` |
| `PAY-` | `payment_id` |
| `DOC-` | `doc_id` документа (счёта или платежа) |
| `E-` | `entity_id` контрагента |

### manifest.json
`schema_version`, `episode_id`, `base_currency`, `period_start` (включительно), `period_end` (**не** включительно), `timezone` (`+05:00`), `counts` (`ledger_rows`, `invoices`, `payments`, `fx_rates`, `documents`), `rounding` (`mode`), `currency_exponents`, `csv_null`, `config_version`. Схема: `manifest.schema.json`.

### Таблицы
| Файл | Поля | Первичный ключ для `get_record` |
|---|---|---|
| `ledger.csv` | `row_id, timestamp, account, debit_minor, credit_minor, currency, entity_id, invoice_id, payment_id` | `row_id` |
| `invoices.jsonl` | `doc_id, invoice_id, entity_id, issued_at, due_at, currency, total_minor, line_items[]` | `invoice_id` |
| `payments.jsonl` | `doc_id, payment_id, timestamp, currency, amount_minor, invoice_refs[]` | `payment_id` |
| `fx.csv` | `date, source_currency, target_currency, rate` | `FX:<date>:<source>:<target>` |

- `line_items[]`: `{description, quantity, unit_price_minor, amount_minor}`; сумма `amount_minor` = `total_minor`.
- `invoice_refs[]`: `{invoice_id, amount_minor}` — распределение платежа по счетам в валюте платежа (как в банковской выписке). Пустой список — платёж без указания счёта. **[утверждено: A]** v1: платёж закрывает только счета в своей валюте, без кросс-валютного распределения.
- `fx.csv` содержит курс **на каждый день** от `period_start − 10 дней` до `period_end + 10 дней` для каждой иностранной валюты эпизода. Так курс нужной даты всегда есть в открытых данных, в том числе для документов на границе периода, и правило «курс на ближайшую дату» не нужно.
- `amount_minor` платежа со знаком: `> 0` — поступление от клиента, `< 0` — возврат клиенту.
- Строки файлов отсортированы по `(timestamp или issued_at или date, ID)`. Логика среды и оценщика **не зависит** от порядка строк.

### policy.json
Открытые правила, которые видит агент:
- курс берётся на **локальную дату документа** (`issued_at` для счёта, `timestamp` для платежа) в часовом поясе манифеста; `1 source_currency = rate target_currency`;
- отчётный период — `[period_start, period_end)` по локальному времени;
- округление после конвертации — `ROUND_HALF_EVEN` до разрядности целевой валюты;
- допуск по сумме — `amount_tolerance_minor` (по умолчанию 1).

Схема: `records.schema.json#/$defs/policy`.

## 4. Модель учёта **[утверждено: A]**

Предложение v1, чтобы данные были простыми и проверяемыми:
- Книга (`ledger.csv`) ведётся в **базовой валюте** (`currency` = `base_currency` во всех строках). Документы бывают в любой валюте.
- В каждой строке ровно одно из `debit_minor` / `credit_minor` больше нуля, второе равно 0.
- Счета: `1010` Деньги, `1200` Дебиторская задолженность, `2900` Невыясненные поступления, `4000` Выручка, `7900` Курсовые разницы.
- Проводки по документам:
  - счёт: Дт 1200 / Кт 4000 на `total × курс(дата счёта)`;
  - платёж: Дт 1010 на `amount × курс(дата платежа)`, Кт 1200 по каждому `invoice_ref` по курсу даты счёта, разница — в 7900, нераспределённый остаток — Кт 2900;
  - возврат: обратные проводки.
- **Инвариант чистой истории:** по каждому документу сумма дебета = сумма кредита; по всей книге тоже.

## 5. Действия

Действие — JSON `{"tool": "<имя>", "args": {...}}`. Схема: `action.schema.json`. Любое действие расходует 1 шаг, включая ошибочное.

| `tool` | `args` | Результат (`observation.result`) |
|---|---|---|
| `list_records` | `table` (`ledger` / `invoices` / `payments` / `fx`), `cursor` (строка или `null`, по умолчанию `null`), `limit` (1–50, по умолчанию 50) | `{table, records[], next_cursor, total}` |
| `get_record` | `table`, `id` (первичный ключ из раздела 3) | `{table, record}` |
| `get_document` | `doc_id` | `{document}` — полный счёт (с `line_items`) или платёж, плюс `doc_type`: `invoice` / `payment` |
| `calculator` | `expression` | `{expression, value}` — `value` десятичная строка |
| `submit` | `findings` (объект `findings.json`) | завершает эпизод |

- `list_records` для `invoices` отдаёт строки **без** `line_items`: за деталями — `get_document`.
- **Курсор** — непрозрачная строка. Тот же курсор на том же эпизоде всегда даёт ту же страницу. Последняя страница: `next_cursor = null`.
- **Калькулятор:** только числа (десятичные, можно с `-`), `+ - * /`, скобки и пробелы. Свой парсер (рекурсивный спуск) над `Decimal` с точностью 34 знака. Никаких `eval`, имён, функций, атрибутов. Деление на ноль, лишние символы, длина больше 200 → ошибка `CALC_ERROR`.

## 6. Наблюдения

Схема: `observation.schema.json`. Поле `kind`:

| `kind` | Когда | Поля |
|---|---|---|
| `initial` | после `reset` | `task`, `manifest`, `policy`, `tools`, `tables`, `steps_used` = 0, `steps_remaining` = 100 |
| `result` | успешное действие | `tool`, `result`, `steps_used`, `steps_remaining` |
| `error` | ошибочное действие | `tool` (или `null`), `error: {code, message}`, `steps_used`, `steps_remaining` |
| `final` | эпизод завершён | `status` (`submitted` / `invalid_findings` / `step_limit` / `time_limit`), `steps_used`, `steps_remaining` |

Коды ошибок: `INVALID_ACTION`, `UNKNOWN_TOOL`, `UNKNOWN_TABLE`, `NOT_FOUND`, `INVALID_ARGS`, `INVALID_CURSOR`, `CALC_ERROR`, `EPISODE_FINISHED`.

**Сообщения об ошибках — фиксированные шаблоны.** В них нет путей к файлам, имён закрытых файлов, сумм эталона, стека вызовов. В `NOT_FOUND` повторяется только ID, который прислал агент.

## 7. Шаги и завершение

- `steps_used` растёт на 1 при каждом `step`, включая ошибки и `submit`.
- `submit` → `terminated = true`, `kind = final`, `status = submitted` (или `invalid_findings`).
- Если 100-й шаг — не `submit`: `truncated = true`, `status = step_limit`, итоговый ответ считается **пустым** (`findings = []`).
- Время: от `reset`. Если при очередном `step` прошло больше 60 с — действие не выполняется, `truncated = true`, `status = time_limit`, ответ пустой.
- `inspection_steps` = число шагов **до** `submit` (сам `submit` не считается). При усечении — все сделанные шаги.
- После завершения любой `step` → `kind = error`, `EPISODE_FINISHED`, шаг не расходуется, флаги прежние, награда 0.
- Награда на промежуточных шагах всегда `0.0`.

## 8. Выводы (findings)

```json
{
  "episode_id": "EP-8K2M4Q7X",
  "findings": [
    {
      "type": "payment_allocation",
      "affected_ids": ["INV-3HZ7QK2D", "PAY-9F4TX1MB"],
      "claimed_amount_minor": 125000,
      "currency": "USD",
      "evidence_ids": ["DOC-5RW2N8CA", "L-0Q7M2ZK4", "L-7TBC4X1P"],
      "explanation": "Платёж 2 500,00 USD по выписке закрывает INV-3HZ7QK2D, в книге на 1200 разнесено только 1 250,00 USD, остаток на 2900."
    }
  ]
}
```

Схема: `findings.schema.json`. **Неверная структура → награда −1, `terminated = true`, `status = invalid_findings`.** Неверной считается:
- не JSON-объект, лишние или отсутствующие поля;
- `episode_id` не совпадает с текущим;
- `type` не непустая строка (до 64 символов); `currency` не непустая строка (до 16 символов);
- `claimed_amount_minor` не целое число (`1.0`, `"100"`, `true` — неверно);
- больше 30 выводов, больше 10 `evidence_ids`, `explanation` длиннее 1000 символов, пустой `affected_ids`.

**Нормализация перед сопоставлением** (соглашения жюри): `affected_ids` и `evidence_ids` трактуются как множества — порядок и повторы не важны. Строки ID не меняются: регистр и пробелы значимы. `currency` и `type` сравниваются точно: валюта в другом регистре или с пробелом — структурно верный, но ложный вывод (FP), а не ошибка структуры. Неизвестный строковый `type` (не из четырёх типов раздела 9) тоже FP: он ни с чем не сопоставляется, остальные выводы оцениваются как обычно. `explanation` в награде не участвует.

## 9. Ошибки: что считается верным ответом **[утверждено: A + C]**

| `type` | Как вносится | `affected_ids` (канон) | `expected_amount_minor`, `currency` | Допустимые наборы доказательств |
|---|---|---|---|---|
| `duplicate_invoice` | Копия счёта: новый `invoice_id`/`doc_id`, тот же контрагент и строки, дата в пределах 0–5 дней, проведена в книге повторно | оба `invoice_id`, отсортированы | `total_minor` дубля, валюта счёта | `{DOC оригинала, DOC дубля}` |
| `payment_allocation` | По выписке платёж закрывает счёт целиком, а в книге на 1200 разнесена только часть (или ничего), остаток на 2900 | `[invoice_id, payment_id]`, отсортированы | нераспределённая сумма, валюта платежа | `{DOC платежа, все строки книги по этому платежу}` |
| `fx_conversion` | Проводка документа в KZT посчитана по курсу другой даты или по искажённому курсу | `[invoice_id или payment_id]` | `|проведено − верно|` в базовой валюте | `{DOC документа, строка книги, FX:<верная дата>:<валюта>:<база>}` |
| `period_cutoff` | Документ с локальной датой вне периода проведён в книге внутри периода | `[invoice_id или payment_id]` | сумма документа, валюта документа | `{DOC документа, строка книги}` |

- Генератор не создаёт двух ошибок с одной парой `(type, affected_ids)`. Оценщик такой эталон всё равно принимает (уникален только `issue_id`) и разводит ошибки максимальным паросочетанием, как в M10/M11.
- `period_cutoff`: дата документа не дальше 7 дней за границей периода, проводка — внутри периода у той же границы.
- `payment_allocation` не вносится, если нераспределённую сумму нельзя однозначно восстановить из проводки (1 минимальная единица валюты платежа дешевле 1 минимальной единицы базовой, например KZT при базе USD). Тогда ошибок этого типа может быть меньше `count.min`; запланированное и внесённое число пишутся в `generation.json` (`errors_planned`, `errors_injected`).
- Каждая запись из любого допустимого набора доступна через инструменты (это проверяет независимый проверщик, задача #17).
- `evidence_ids` агента засчитываются, если **содержат** хотя бы один допустимый набор целиком. Лишние ID не штрафуются.
- Эталон никогда не требует факта, которого нет в открытых записях.

## 10. Сопоставление и награда

**Вывод — TP**, если для какой-то несопоставленной ошибки эталона одновременно:
1. совпадает `type`;
2. нормализованные `affected_ids` равны каноническим;
3. совпадает `currency`;
4. `|claimed_amount_minor − expected_amount_minor| ≤ amount_tolerance_minor`;
5. `evidence_ids` содержат хотя бы один допустимый набор;
6. все `evidence_ids` существуют в открытых данных эпизода (записи таблиц, ключи FX, документы): ссылка на отсутствующий ID даёт FP. Множество публичных ID оценщику передают среда и `judge_adapter.score_episode`.

**Алгоритм (детерминированный):** максимальное паросочетание в двудольном графе «выводы — ошибки эталона» (ребро — все условия TP). При нескольких максимальных выбирается лексикографически наименьшая последовательность пар `(issue_id, индекс вывода)`: ошибки по `issue_id`, для каждой — вывод с наименьшим индексом, если после этого ещё достижима максимальная мощность. Остальные выводы — FP (в том числе повторы верного вывода), несопоставленные ошибки — FN. В эпизодах нашего генератора ключ `(type, affected_ids)` не повторяется, поэтому там каждый вывод подходит не более чем к одной ошибке; для эталона с повторами (M10/M11) паросочетание остаётся максимальным.

**Метрики:** `P = TP/(TP+FP)`, `R = TP/(TP+FN)`, при нулевом знаменателе 0. `F1 = 2TP/(2TP+FP+FN)`; если эталон и выводы пусты — `F1 = 1`; если эталон пуст, а выводы есть — `F1 = 0`.

**Награда:** `reward = clip(2·F1 − 1 − 0.002·inspection_steps, −1, 1)`. Неверная структура — `−1`. Возврат эпизода = эта награда. Экспериментальная награда, если появится, считается рядом и показывается отдельно; общая не меняется.

Код нормализации, допусков и сопоставления — открытый: `grader/`.

## 12. truth.json и provenance.json

`truth.json` (схема `truth.schema.json`): `schema_version`, `episode_id`, `issues[]` (`issue_id`, `type`, `affected_ids`, `expected_amount_minor`, `currency`, `amount_tolerance_minor`, `evidence_sets[][]`, `scenario` или `null`), `distractors[]` (`distractor_id`, `kind`, `record_ids[]`).

`provenance.json`: `episode_id`, `generator_version`, `clean_history_sha256`, `mutations[]` — для каждой ошибки причинное изменение: `{issue_id, type, changes: [{table, record_id, field, before, after}]}` (его читает `generator.explain`), и `clean_history_diff` — полный обратимый журнал отличий открытых таблиц от чистой истории. По нему `grader.clean_history` восстанавливает книги до внесения ошибок и сверяет их с `clean_history_sha256` и балансом.
Полный формат и значения служебных полей (`__created__`, `__deleted__`, `__copy_of__`, `allocated_minor:<id>`, `rate_used`): [DATA.md, раздел 3.3](DATA.md#33-формат-provenancejson).

`issue_id` — случайные строки `ISS-XXXXXXXX`; они же служат метками-«канарейками» при поиске утечек.

## 13. Конфиг генератора

Схема: `config.schema.json`. Основное:
- `config_version` — строка версии конфига (`train-v1`, `dev-v1`);
- `mode` — `train` / `eval`;
- `company`: `archetype` (`importer` / `saas` / `distributor`), `base_currency`, `timezone`, `foreign_currencies[]`;
- `size`: диапазоны `ledger_rows` [200, 2000], `documents` [20, 200];
- `errors.<type>`: `enabled`, `count: [min, max]` — **каждый тип настраивается отдельно**;
- `interactions.<scenario>`: `enabled`, `count: [min, max]`;
- `distractors.<kind>`: `enabled`, `count: [min, max]`;
- `clean: true` — принудительно 0 ошибок (отвлекающие случаи остаются);
- `max_errors` — не больше 12.

Жюри передаёт свои seed и конфиги: генератор обязан принять **любое** валидное сочетание.

## 15. Детерминизм

- Все случайности — из `random.Random`, засеянного `int.from_bytes(sha256(f"{seed}:{stream}").digest()[:8], "big")`. Потоки: `content` (суммы, даты, контрагенты), `ids` (все ID), `errors` (выбор и внесение ошибок).
- Смена потока `ids` не меняет содержание — на этом держатся парные проверки со сменой ID.
- Запрещено в ядре: `datetime.now()`, `time.time()` (кроме таймера эпизода), итерация по `set`/`dict` без сортировки, `float` для денег и курсов, `hash()`.
- JSON пишется через `common.jsonio.canonical_dumps` (сортировка ключей, без пробелов), файлы — UTF-8 с LF.
- `generation.json` хранит `sha256` каждого public-файла: тот же `(seed, config, generator_version)` → те же хэши.

### Отпечаток эпизода
- `public_sha256` — `{имя файла: sha256 hex байтов файла}` для шести public-файлов (`manifest.json`, `ledger.csv`, `invoices.jsonl`, `payments.jsonl`, `fx.csv`, `policy.json`).
- `episode_sha256 = sha256(canonical_dumps(public_sha256).encode("utf-8")).hexdigest()`. Оба поля лежат в `private/generation.json`.
- Критерий детерминизма: тот же `(seed, config, generator_version)` → тот же `episode_sha256` (в том числе при разном `PYTHONHASHSEED`).
- Сервер при загрузке эпизода (и сгенерированного, и `--episode`) пересчитывает хэши (`env.fingerprint.verify_episode`) и сверяет с `generation.json`. Расхождение, отсутствие файла или полей → ошибка протокола `EPISODE_INVALID`; сервер продолжает работать.
- Отпечаток пишется в журнал оценщика (`episode_sha256`) и не попадает в `observation`/`info`.

## 16. Интерфейс среда ↔ оценщик (B ↔ C)

Среда (B) не считает награду сама, а вызывает функцию оценщика (C):

```python
# grader/evaluate.py
def evaluate(findings_obj, truth: dict, episode_id: str, inspection_steps: int,
             public_ids=None) -> dict:
    """public_ids - множество ID открытых данных эпизода (None - без проверки доказательств).
    Возвращает {"valid": bool, "reward": float, "error": str | None,
                   "metrics": {"tp", "fp", "fn", "precision", "recall", "f1"}}"""
```

- `findings_obj` — то, что агент прислал в `submit.args.findings`, **как есть** (любой JSON). Проверку структуры (раздел 8) делает оценщик.
- При усечении (`step_limit`, `time_limit`) среда передаёт `{"episode_id": <текущий>, "findings": []}`.
- `valid = false` → среда ставит `status = invalid_findings`, `reward` = −1 из ответа оценщика.
- `error` — текст для журнала оценщика; агенту в режиме `eval` не показывается.
- В режиме `train` среда возвращает `reward` и `info.metrics`; в `eval` — `reward = 0.0`, ответ оценщика остаётся на стороне сервера.
