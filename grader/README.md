# Оценщик (роль C)

Реализация разделов 8–10 и 16 `docs/contract.md`, только стандартная библиотека
Python 3.11+. Общие схемы, генератор, среда и политики не изменены.

## Подключение к среде

```python
from grader.evaluate import evaluate

result = evaluate(findings_obj, truth, episode_id, inspection_steps, public_ids=episode.public_ids())
# public_ids: ID открытых записей и документов; несуществующее доказательство -> FP
# {"valid": bool, "reward": float, "error": str | None,
#  "metrics": {"tp", "fp", "fn", "precision", "recall", "f1"}}
```

Среда передаёт ответ агента как есть, а при усечении — объект с текущим
`episode_id` и пустым `findings`. `inspection_steps` не включает `submit`.
Неверный ответ даёт `valid=False`, награду −1 и нулевые TP/FP/P/R/F1;
FN равен числу ошибок эталона. Это диагностические метрики, сопоставление
для неверной структуры не выполняется. Дефект эталона или отрицательный/
нецелый счётчик шагов вызывает `ValueError` на стороне сервера.

В train среда возвращает агенту только награду и метрики. В eval она хранит
результат у себя и возвращает награду 0. Режимы, повторный submit, бюджет,
разбор сырых JSON-строк и таймер реализует владелец `env/`.

Проверка использует существующие `schemas/findings.schema.json` и
`schemas/truth.schema.json`. Денежные поля дополнительно требуют именно
Python `int`: `true`, `1.0`, строки, NaN и Infinity не принимаются. Лимиты
проверяются до нормализации: повтор 11 одинаковых evidence ID не обходит
ограничение в 10 элементов.

Matcher не меняет строки ID: регистр и пробелы значимы (`" INV-1"` и
`"INV-1"` - разные ID), удаляются только повторы внутри списков. Пустые или
неизвестные `type`, ID и `currency` структурно верны: такой вывод не
отклоняет ответ целиком, а просто становится FP. Выводы обрабатываются в порядке отправки, эталон — по `issue_id`.
Одна ошибка засчитывается один раз; следующие копии вывода становятся FP.
Сумма сравнивается включительно по допуску эталона; при загрузке эпизода он
ограничивается допуском, опубликованным в `policy.json` (берётся минимум). Нужен хотя бы один
полный допустимый набор доказательств; дополнительные ID допустимы.
`explanation` не участвует в награде. `match()` возвращает приватные детали
для диагностики; `evaluate()` возвращает только агрегированные метрики.

Награда: `clip(2 * F1 - 1 - 0.002 * inspection_steps, -1, 1)`.
При обоих пустых списках F1 = 1, P = R = 0. На ошибочном эпизоде пустой
ответ даёт −1; на чистом эпизоде после 100 шагов — 0.8.

## Независимый сертификат

```powershell
python -m grader.certificate episodes/train/EP-0HJPAE81
```

Команда читает открытые CSV/JSON/JSONL и `private/truth.json`, пишет
`private/certificate.json`. Код выхода: 0 — подтверждено, 1 — проверка
не прошла, 2 — не удалось прочитать вход или эталон нарушает контракт.
API: `certify(public_records, truth, provenance)`; для эпизода на диске:
`certify_episode(path)`. `valid` требует доказанной чистой истории: без
provenance или без журнала эпизод не сертифицирован. Ручные мини-эпизоды
тестов без журнала: `certify(..., require_history=False)` или
`python -m grader.certificate --no-history <папка>`.

Проверщик не вызывает генератор или matcher. Пересчёт ошибок использует
документы, их открытые ссылки, книгу, FX, манифест и политику; provenance
нужен только для восстановления чистой истории (её хэш сверяется, журнал
на веру не принимается). Каждый допустимый набор доказательств проверяется отдельно.
Вычисленная сумма должна точно совпадать с эталоном: допуск ответа агента
не скрывает дефекты самого эталона.

Поддержаны четыре типа ошибок, оба совмещённых сценария и четыре вида
отвлекающих случаев из контракта. Проверяются доступность доказательств,
баланс текущей книги по документам, локальный период, разрядность валют
и округление `ROUND_HALF_EVEN`. Порядок строк не влияет на вывод.

Границы сертификата:

- Чистая история (до внесения ошибок) восстанавливается по открытым данным
  и `provenance.clean_history_diff`. `clean_history_balance`: хэш совпадает
  с `clean_history_sha256`, книга сходится по каждому документу.
  `clean_history_rules` (`grader.consistency`): каждый документ чистой
  истории проведён по правилам контракта, каждое ненулевое распределение
  видно строкой Кт 1200, дублей счетов нет, курсы не менялись; каждое
  отличие открытых данных от чистой истории покрыто ошибкой эталона своего
  типа, и каждая ошибка эталона опирается на реальное изменение. Новый
  документ — только копия-дубль, других дублей в открытых данных нет; сдвиг
  дат — только ошибка периода, и документ перепроведён по правилам новой
  даты (даже если проводки не изменились); ошибка курса — один неверный
  курс, распределения и счета учёта те же; ошибка распределения — меняется
  только распределение заявленного счёта; контрагент и ссылки строк книги
  не меняются ни одной ошибкой. Провенанс того же эпизода
  (`episode_id`), его `mutations` — ровно ошибки эталона с теми же типами.
  Эпизод без журнала получает `status=not_checked` в обоих пунктах и
  `valid=false`.
- ID уникальны внутри своей таблицы: одна и та же строка может быть ID
  строки книги, документа, счёта, платежа и контрагента (жюри меняет ID по
  пространствам независимо). Если строка — и invoice_id, и payment_id,
  проверяются оба прочтения, и доказательство должно быть однозначным.
- Ошибка курса у платежа: проверяется, что существует один курс, дающий
  после округления ROUND_HALF_EVEN и Дт 1010, и остаток 2900 (точное
  пересечение отрезков, а не пропорция сумм).
- Распределения платежа восстанавливаются совместно по всем его строкам:
  строка Кт 1200 по каждому счёту и остаток 2900 (он фиксирует сумму
  распределений). Если и совместно сумма неоднозначна, сертификат её не
  подтверждает и не подставляет сумму из эталона.
- Для возвратов проверяются покрывающие исходные платежи, общая сумма
  возвратов и обратные проводки. Явной ссылки `refund_of` в контракте нет,
  поэтому причинная связь с единственным исходным платежом не доказывается.
- Полнота эталона доказывается относительно чистой истории: каждое
  отличие от неё покрыто ошибкой. Ошибку, которую генератор внёс бы уже в
  чистую историю, ловят правила учёта `clean_history_rules`, а не журнал.

## Проверки и галерея атак

```powershell
python -m scripts.check
```

Тесты роли C находятся в `tests/test_grader*.py` и `tests/test_attacks.py`.
Параметризованные проверки покрывают следующие атаки:

| Попытка | Результат при 0 шагах |
|---|---|
| Пустой ответ при наличии ошибок | −1 |
| 30 находок, только одна верна | 1 TP + 29 FP; награда `4/31 - 1` |
| 10 копий верного вывода | 1 TP + 9 FP; награда `4/11 - 1` |
| Несуществующие affected ID | FP |
| Изменённый регистр ID | FP |
| Лишний affected ID | FP |
| Чужие evidence ID | FP |
| Неполный набор доказательств | FP |
| Фрагменты двух альтернативных наборов | FP |
| Другая валюта | FP |
| Сумма за пределом допуска | FP |
| Отрицательная сумма вместо положительной | FP |
| Инъекция в explanation | Результат не меняется |
| Подмена episode_id | Неверная структура, −1 |
| 31 находка / 11 evidence / 1001 символ объяснения | Неверная структура, −1 |
| Неизвестный тип, пропущенные/лишние поля | Неверная структура, −1 |
| Float, bool, строка, NaN/Infinity вместо целого | Неверная структура, −1 |
| Строка со сломанным JSON вместо объекта | Неверная структура, −1 |

Hypothesis проверяет максимум oracle, ухудшение при потере TP, штраф за
FP, отсутствие выгоды от повторов, монотонный штраф за шаги и диапазон
награды. Дополнительно проверяются перестановки и взаимно однозначная
смена ID. В репозитории нет полного исходного списка пяти свойств от
организаторов: эти проверки опираются на утверждённую формулу и контракт.

`.gitignore` исключает локальные настройки редакторов, окружения, кэши,
логи и отчёты прогонов. Исходники, `schemas/`, `episodes/` и сдаваемые
`trajectories.jsonl` остаются под контролем Git. Конфликты правок одного
исходного файла решаются разделением задач и согласованием с его владельцем.
