# Оценщик (роль C)

Реализация разделов 8–10 и 16 `docs/contract.md` и соглашений matcher жюри,
только стандартная библиотека Python 3.11+. Схема findings согласована с
обработкой неизвестного строкового типа как FP.

## Подключение к среде

```python
from grader.evaluate import evaluate

result = evaluate(findings_obj, truth, episode_id, inspection_steps, public_ids=episode.public_ids())
# public_ids: ID открытых записей и документов; несуществующее доказательство -> FP
# {"valid": bool, "reward": float, "error": str | None,
#  "metrics": {"tp", "fp", "fn", "precision", "recall", "f1"}}
```

Среда передаёт ответ агента как есть, а при усечении — объект с текущим
`episode_id` и пустым `findings`. `inspection_steps` не включает `submit`.
Неверный ответ даёт `valid=False`, награду −1 и нулевые TP/FP/P/R/F1;
FN равен числу ошибок эталона. Это диагностические метрики, сопоставление
для неверной структуры не выполняется. Дефект эталона или отрицательный/
нецелый счётчик шагов вызывает `ValueError` на стороне сервера.
Адаптер `judge_adapter.score_episode` преобразует невалидный ответ в
`return=-1` и `null` во всех полях метрик, как требует жюри.

В train среда возвращает агенту только награду и метрики. В eval она хранит
результат у себя и возвращает награду 0. Режимы, повторный submit, бюджет,
разбор сырых JSON-строк и таймер реализует владелец `env/`.

Проверка использует существующие `schemas/findings.schema.json` и
`schemas/truth.schema.json`. Денежные поля дополнительно требуют именно
Python `int`: `true`, `1.0`, строки, NaN и Infinity не принимаются. Лимиты
проверяются до нормализации: повтор 11 одинаковых evidence ID не обходит
ограничение в 10 элементов.

Matcher сравнивает ID точно, включая регистр и пробелы; повторы внутри
списков трактуются как множество. Он строит максимальное паросочетание;
при равенстве выбирает лексикографически наименьшие пары
`(issue_id, индекс вывода)`. Разные ошибки могут иметь одинаковые
`(type, affected_ids)`; `issue_id` должен оставаться уникальным.
Одна ошибка засчитывается один раз; лишние копии вывода становятся FP.
Неизвестный строковый `type` — отдельный FP, остальные находки оцениваются.
Нестроковый `type` — ошибка структуры всего ответа.
Сумма сравнивается включительно по допуску эталона. Нужен хотя бы один
полный допустимый набор доказательств; дополнительные публичные ID допустимы,
но любой несуществующий evidence ID делает вывод FP.
`explanation` не участвует в награде. `match()` возвращает приватные детали
для диагностики; `evaluate()` возвращает только агрегированные метрики.

Награда: `clip(2 * F1 - 1 - 0.002 * inspection_steps, -1, 1)`.
При обоих пустых списках F1 = 1, P = R = 0. На ошибочном эпизоде пустой
ответ даёт −1; на чистом эпизоде после 100 шагов — 0.8.

## Независимый сертификат

```powershell
python -m grader.certificate episodes/train/EP-8K2M4Q7X
```

Команда читает открытые CSV/JSON/JSONL, `private/truth.json`,
`private/provenance.json` и `private/clean_history.json`; пишет только
`private/certificate.json`. По умолчанию CLI требует полную проверку истории.
Код выхода: 0 — подтверждено, 1 — проверка не прошла или закрытого доказательства
не хватает, 2 — не удалось прочитать вход или эталон нарушает контракт.

Для старых эпизодов без снимка есть явный частичный режим:

```powershell
python -m grader.certificate episodes/train/EP-8K2M4Q7X --public-only
```

API `certify(public_records, truth)` и `certify_episode(path)` сохраняют
совместимость с проверками публичных доказательств. Для полного сертификата
передайте `require_history=True`; в `certify` также передаются именованные
`provenance` и `clean_history`, а `certify_episode` читает их с диска.
`fully_verified=True` возможен только при успешной проверке и публичных
доказательств, и исходной истории. Без снимка `clean_history_balance.status`
равен `not_checked`, а `fully_verified=False`. Предоставленное, но неверное
доказательство делает сертификат невалидным даже в частичном режиме.

Проверщик не вызывает генератор, matcher или reward. Пересчёт использует
документы, их открытые ссылки, книгу, FX, манифест и политику. Каждый допустимый
набор доказательств проверяется отдельно. Вычисленная сумма должна точно
совпадать с эталоном: допуск ответа агента не скрывает дефекты самого эталона.

Поддержаны четыре типа ошибок, оба совмещённых сценария и четыре вида
отвлекающих случаев из контракта. Проверяются доступность доказательств,
баланс текущей книги по документам, локальный период, разрядность валют
и округление `ROUND_HALF_EVEN`. Порядок строк не влияет на вывод.

Границы сертификата:

- Полная проверка зависит от закрытого снимка и полного журнала от генератора
  (формат ниже). Старый хэш с краткими описаниями мутаций не заменяет их.
- Если округление делает обратный пересчёт распределения неоднозначным,
  сертификат не подтверждает сумму. Он не подставляет сумму из эталона.
- Полный сертификат FX-ошибки платежа с нераспределённым остатком требует
  дополнительного доказательства применённого курса, которого нет в текущем
  контракте truth. Пока такой случай отклоняется с явной причиной; проверка
  `test_fx_payment_with_remainder_is_explicitly_unverified_without_applied_rate`
  воспроизводит это ограничение. Полностью разнесённые FX-платежи поддержаны.
- Для возвратов проверяются покрывающие исходные платежи, общая сумма
  возвратов и обратные проводки. Явной ссылки `refund_of` в контракте нет,
  поэтому причинная связь с единственным исходным платежом не доказывается.
- Частичный сертификат проверяет перечисленные ошибки и отвлекающие случаи;
  он не доказывает, что генератор перечислил все возможные ошибки.

## Вход от A для проверки исходной истории

Генератор сохраняет `private/clean_history.json` непосредственно перед
внесением ошибок, после добавления законных отвлекающих случаев:

```json
{
  "schema_version": "1.0",
  "episode_id": "EP-8K2M4Q7X",
  "tables": {"ledger": [], "invoices": [], "payments": [], "fx": []}
}
```

Массивы содержат полные исходные записи; денежные значения — целые числа,
пустые ссылки — JSON null, FX — десятичные строки. Manifest и policy остаются
неизменными при внесении ошибок и берутся из public. Хэш совместим с
`generator.build.history_digest`: `canonical_dumps(tables)` в UTF-8 после
сортировки ledger по `(timestamp, row_id)`, invoices по `(issued_at, invoice_id)`,
payments по `(timestamp, payment_id)`, FX по `(date, source_currency, target_currency)`.
Время сравнивается как datetime с часовым поясом. Полученный SHA-256 должен
совпасть с `provenance.clean_history_sha256`.

В каждую `provenance.mutations[]` добавляется `record_changes`: список объектов
с полями `table`, `record_id`, `before`, `after`. `before` и `after` — полные
записи; при создании `before=null`, при удалении `after=null`. Простого ID
удалённой записи недостаточно. Существующие краткие `changes` можно сохранить
для `generator.explain`, но они не заменяют полный журнал.

Порядок `mutations` и `record_changes` — хронологический, значимый. Сейчас
генератор сортирует мутации по `issue_id`; A должен сохранить порядок операций
для нового журнала, включая промежуточные созданные и удалённые строки.
Каждая мутация ссылается на существующий `issue_id` и соответствующий `type`.
Для общего изменения совмещённого сценария допустима пустая `record_changes`
у второй ошибки, если изменение её документа подтверждено другой мутацией
того же сценария. Результат replay обязан точно совпасть с финальными таблицами
без учёта порядка записей; порядок `line_items` сохраняется.

Оценщик независимо проверяет исходные документы и проводки, хэш, значения
`before`, принадлежность изменений затронутым документам, полноту replay и
финальные доказательства truth. Дополнительно исключаются дубли в исходной
истории и незаявленные отклонения проводок/периода в конечных документах.
Он не регенерирует исходные данные по seed.
При переименовании ID жюри снимок и журнал также преобразуются, а хэш снимка
пересчитывается; перестановка строк сама по себе хэш не меняет.
После подключения формата A обновление хэша должен добавить владелец парных
преобразований D: текущий `scripts/transform_episode.py` его не пересчитывает.

В ver3 реализован потребитель этого формата со стороны C. Сохранение снимка
и полного хронологического журнала в `generator/` остаётся задачей A.

## Проверки и галерея атак

```powershell
python -m scripts.check
```

Тесты роли C находятся в `tests/test_grader*.py` и `tests/test_attacks.py`.
Параметризованные проверки покрывают следующие атаки:

| Попытка | Результат при 0 шагах |
|---|---|
| Пустой ответ при наличии ошибок | −1 |
| 30 находок, только одна верна | 1 TP + 29 FP; награда `4/31 - 1` |
| 10 копий верного вывода | 1 TP + 9 FP; награда `4/11 - 1` |
| Несуществующие affected ID | FP |
| Изменённый регистр ID | FP |
| Лишний affected ID | FP |
| Чужие evidence ID | FP |
| Неполный набор доказательств | FP |
| Фрагменты двух альтернативных наборов | FP |
| Другая валюта | FP |
| Сумма за пределом допуска | FP |
| Отрицательная сумма вместо положительной | FP |
| Инъекция в explanation | Результат не меняется |
| Подмена episode_id | Неверная структура, −1 |
| 31 находка / 11 evidence / 1001 символ объяснения | Неверная структура, −1 |
| Неизвестный строковый тип | FP, остальные находки оцениваются |
| Нестроковый тип, пропущенные/лишние поля | Неверная структура, −1 |
| Float, bool, строка, NaN/Infinity вместо целого | Неверная структура, −1 |
| Строка со сломанным JSON вместо объекта | Неверная структура, −1 |

Hypothesis проверяет максимум oracle, ухудшение при потере TP, штраф за
FP, отсутствие выгоды от повторов, монотонный штраф за шаги и диапазон
награды. Дополнительно проверяются перестановки и взаимно однозначная
смена ID. В репозитории нет полного исходного списка пяти свойств от
организаторов: эти проверки опираются на утверждённую формулу и контракт.

`.gitignore` исключает локальные настройки редакторов, окружения, кэши,
логи и отчёты прогонов. Исходники, `schemas/`, `episodes/` и сдаваемые
`trajectories.jsonl` остаются под контролем Git. Конфликты правок одного
исходного файла решаются разделением задач и согласованием с его владельцем.
